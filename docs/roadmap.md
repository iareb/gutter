# Roadmap

How we get from an empty repo to release 0.1. Milestones and their rationale are in the [design document](design.md#roadmap-and-open-questions); this file breaks them into concrete steps.

## Workflow

Gutter has a single maintainer, so there are no pull requests: work lands directly on `main`.

1. The agent makes the change in the working tree and runs it locally.
2. The agent hands over a commit message and a short manual checklist (how to try it in under 5 minutes).
3. The maintainer runs the checklist, commits and pushes.
4. CI runs on every push to `main`. A red CI is fixed before anything else.

Spikes (M0.5) live on throwaway branches named `spike/<name>` that are never merged; only their write-up in `docs/spikes/` lands on `main`.

### Synthetic test corpus

Copyrighted comics cannot go in the repo, so a script generates pages designed for testing:

- fine stripe patterns and tiny text, which make any quality loss obvious;
- large page numbers, which make skipped pages visible;
- edge cases: 10,000 px pages, AVIF, odd file names, a corrupt archive, a double-page spread.

## M2 — Gesture engine

Zoom, pan and page turns by touch, mouse, trackpad and keyboard, with the rule from the design doc: one gesture, one action. All input goes through one module, a state machine in the TypeScript core that sees normalized events from small per-platform adapters. Thresholds are constants in one place for now; a settings screen comes later. Windows trackpad pinch cannot be tested yet (no laptop with a trackpad): it follows the documented Chromium behavior and gets checked when a trackpad is available.

## M2.5 — CBR

Moved up from M5, before the reading modes: preloading and the memory budget in M3 depend on what a page costs in each format, and in a solid RAR archive a page can only be read after the ones before it. The [`cbr-library` spike](spikes/cbr-library.md) chose the `rars` crate (pure Rust, Apache-2.0). Same workflow as the other milestones: one step at a time, each with a way to try it.

| Step | Content | How to try it |
| --- | --- | --- |
| 2.5.1 Page source | The archive format is recognized from the file's first bytes, not from its extension (ZIP, RAR; anything else gets a clear message). ## M3 — Reading modes

What is left of the reader after the gesture engine: pages ready before they are asked for, a memory budget that holds on a phone, double page, reading right to left, and continuous vertical scroll. The plan is ordered so that each step stands on the one before: first what a page costs and a cache that respects a budget, then preloading, then the modes, which all draw from that cache.

**Where it starts.** A page change fetches the bytes, decodes them at the size shown and draws; nothing is kept for the next page, so a turn takes about 0.15 s on Windows and 0.3 to 0.4 s on the phone (the design aims at one frame, 16 ms, with a preloaded page). The phone's whole process held about 490 MB after reading 16 pages of a 116 MB volume (native heap 40 to 80 MB, graphics about 270 MB, the same for CBZ and CBR), and Windows about 430 MB of webview after the M1 checklist, both well over the design's targets; where the graphics memory comes from is not known yet. Pages of 7000 × 10000 pixels are decoded whole at high zoom (280 MB).

**Decisions behind this plan** (written as recommendations; changing one changes the steps it names):

- **Fit modes.** Page by page the page is always fitted to the screen. Fit to width exists only in vertical scroll, where it is the point. A page taller than the screen in a page mode would be a zoomed page (which the wheel, arrows and keys cannot turn, by the M2.6 rule) and a mouse user could not turn it. The design doc's "fit to width, to height, to screen" shrinks to that.
- **Settings.** The reading mode, the direction and what else the view menu holds are saved as global defaults in a small settings store from step 3.5; the position in each volume and per-volume overrides come with the library (M4, SQLite).
- **Order.** Cache and preloading first, then direction (small, and the other modes need it), then double page, then vertical scroll, the biggest piece. If vertical scroll matters more than double page to the maintainer, 3.6 and 3.7 swap places.
- **Huge pages.** Whether pages above about 8000 pixels need decoding only the visible part is decided by the numbers of step 3.1, and done in step 3.9 if it is needed. *Decided in 3.1:* not in M3. Tiles cut from the page in the webview still decode the whole image first, so they would not lower the peak; a region decode would have to be done in Rust, after 0.1.

| Step | Content | How to try it |
| --- | --- | --- |
| 3.1 What a page costs | A development overlay (not in release builds) with, per page: time to fetch, to decode, to draw, bytes of the decoded bitmap, and how many bitmaps are alive. Write-up in `docs/spikes/page-memory.md`; the design doc's targets (viewer memory below 300 MB on desktop and 150 MB on mobile, a page change below one frame) are revised from the numbers, and the memory budget per platform is set | The write-up has the numbers for the three devices and a decision for each question; the overlay shows them live. **Done**: [`page-memory`](spikes/page-memory.md). ## M4 — Library

Until now Gutter opens one file at a time and forgets it when it closes. M4 makes it the place where the reader's comics are: a grid of covers, each volume reopening where it was left, and the choices made for one volume (a manga read right to left) kept for it.

**Where it starts.** A file is opened through the system picker and read; nothing is saved but the global settings of the View menu (`core/settings.ts`, in the webview's storage). On Android the picker gives a `content://` address that the app may lose the right to read once it is closed, and the bar says "Comic" because such an address carries no file name.

**Decisions behind this plan** (written as recommendations; changing one changes the steps it names):

- **What opens first.** The library, with "Continue reading" at the top: one tap gets back into the last volume. Opening straight into the last volume would hide the library on every start.
- **The database.** SQLite in Rust with `rusqlite` (bundled, so the same on every platform), behind a few Tauri commands, tested with `cargo test`. The design document said "SQLite via Tauri plugin": the SQL plugin would put the queries in the webview, where they cannot be tested without it.
- **What a volume is.** The file at a path or address, plus a fingerprint (its size and a hash of its first and last 64 KB): a volume moved or renamed and added again keeps its place and its cover.
- **Thumbnails.** Made in Rust from the first page, about 300 pixels wide, saved as JPEG in the app's cache folder, served by a `thumb://` address like the pages. The design document said WebP: the `image` crate only writes lossless WebP, several times bigger. A thumbnail is made once, in the background, and made again only if the file changed.
- **Folders.** On a computer, "Add folder" adds every CBZ and CBR in it and in its subfolders, once; watching a folder for new files comes later. On Android the system's folder picker has to be tried first (step 4.1).
- **Per-volume choices.** The direction and the page mode chosen while reading a volume are kept for that volume; the View menu's choices are the defaults for a volume never opened. Removing a volume from the library never deletes the file.

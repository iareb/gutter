# M2.5 checklist — CBR

Run on the built app before closing M2.5, on each platform. Mark each cell **ok**, **—** (not applicable) or the number of the issue opened for it. A failure becomes an issue with the bug report form and, when a file made it fail, a volume in the corpus (or a fixture) and a test.

**Setup.** Generate the volumes with `pnpm corpus`; the CBR ones need the `rar` command line (WinRAR, or the `rar` package), which `pnpm corpus` looks for by itself. Files are in `corpus/generated/`. Desktop: build with `pnpm tauri build --no-bundle` and start `src-tauri/target/release/gutter` (`gutter.exe` on Windows). Android: `pnpm tauri android dev`, then copy the files to `Download` with `adb push` (once per file, from `corpus/generated/`):

```bash
adb push corpus/generated/basic-rar5.cbr /sdcard/Download/
```

For item 6, copy `basic-rar5.cbr` under the name `basic-as.cbz` first. Items 17 and 18 use your own files. The two `large-*.cbr` files are 116 MB each: leave them out of the phone if it has little room, and mark items 7 to 10 on Android with —.

**Devices.** Windows: mouse and keyboard. Linux: the laptop. Android: touch only, with the phone upright. Every volume has a page number drawn large on each page, so a page can be told without the header.

**The phone** (Motorola edge 60, Android 16): every file was opened through the system picker, found with its search box and tapped, so each one reached the app as a `content://` URI, the real path; pages were turned with real taps and swipes sent by `adb shell input`, so these are real touches; the double tap and the ten fast taps of item 7 are DevTools touch events, which `adb` cannot send. Turn times: 20 swipes in a plain CBR, median 0.59 s a page; 20 taps in a plain CBR and in a solid one, median 0.35 s; 15 turns forward in `large-solid.cbr`, median 0.43 s and none over 0.6 s; ten back, median 0.40 s; the maintainer's 55-page CBR, median 0.49 s and 0.83 s the slowest. A jump to the last page of `large-solid.cbr` (the End key sent by the script; a phone has none) took 2.5 s. Item 18 on the phone: with 16 pages of `large-solid.cbr` read the app's native heap is 77 MB (the window of decoded pages is about 40 MB of it), which is what "the app's own memory" means there; the total of the process (PSS) is 533 MB, and 492 MB for the same volume as a CBZ, 461 MB as a plain CBR: most of it is graphics (about 270 MB, the canvas), the same for every format, and it is the memory budget to set in M3.

"Automated" means the action was sent by a script and the result read from the page, as in the [M1](m1.md) and [M2](m2.md) checklists: on Windows with real key and wheel events sent through the webview's DevTools protocol (the release build); "WSL" is WebKitGTK in WSL with DOM events, on files made on Windows. Only the system file picker was bypassed. Item 17 on Windows was run on the maintainer's own file, read-only.

Known limits, not failures: on Android the options bar says "Comic" instead of the file name, because the picker returns a `content://` address and the app takes the name from the path (fixing it needs a query to the content provider);  password-protected archives are not read (the message says so); a RAR file that ends too soon is not opened at all, though the pages before the cut could be read in principle (the cost of the pure Rust reader, see the [spike](../spikes/cbr-library.md)); multi-volume sets (`.part1.rar`) are not read; CB7 is after 0.1; jumping to a page far ahead in a solid archive takes a moment, and there is no slider for it yet (M2.6); the pages of a CBR are not preloaded (M3).
